# Quick Wins Implementation Plan

## Goal

Implement the highest-value, lowest-effort remaining TODO items from `suggestions.md`:
1. Reply / thread (quote-and-reply model)
2. Auto-session naming

## 1. Reply / Thread (Quote-and-Reply)

**Design**: Option A — quote-and-reply. Tapping a message adds a quoted reference to the composer; the quoted text is prepended to the sent prompt. No visual thread nesting.

### Changes

**A. Session state (`app/session/[id].tsx`)**
- Add `replyTo` state: `{ messageID: string; text: string; role: string } | null`
- Add `setReplyTo` setter
- Add `cancelReply` action

**B. Composer UI (`app/session/[id].tsx`)**
- When `replyTo` is non-null, render a quoted preview bar above the `TextInput`:
  - Shows "In reply to [role]" + truncated quoted text
  - Has a dismiss (X) button
  - Styled distinctly (e.g., left border accent, slightly different background)
- `handleSend` prepends the quoted text to the outgoing prompt:
  - Format: `> [quoted text]\n\n[user input]`
  - Only when `replyTo` is set
  - Clear `replyTo` after successful send

**C. Message long-press (`src/components/chat/MessageBubble.tsx`)**
- Add `onReply` prop to `MessageBubble` props interface
- In the long-press action sheet (currently only reactions for non-user messages, edit/revert for user messages):
  - For **all** messages, add a "Reply" button
  - On press, call `onReply(message.id, message.role, messageText)`
- `messageText` = concatenated text parts (same logic as `textParts.map(...).join("\n")` in MessageBubble)

**D. Wire up (`app/session/[id].tsx`)**
- Pass `onReply` handler to `MessageBubble` via the render item
- Handler extracts text from the message and sets `replyTo`

### Edge cases
- Empty message text: still allow reply, quote shows `[empty message]`
- Very long messages: truncate quoted text to ~200 chars in the preview bar
- Sending while reply is active: always clear reply after send (success or failure)
- Reverting a message that is currently quoted: clear reply if the quoted messageID no longer exists

## 2. Auto-Session Naming

**Design**: After the first user message is sent, if the session still has no title, generate one from the message text. Use simple truncation first; LLM summarization is deferred.

### Changes

**A. Session store (`src/stores/sessions.ts`)**
- Add `autoNameSession(sessionID: string, text: string)` action
- Logic:
  1. Check if session already has a non-empty title — skip if so
  2. Generate candidate: `truncate(stripMarkdown(text), 40)` + `"..."` if truncated
  3. Call `client.session.update(sessionID, { title: candidate })`
  4. On success, update local session state with new title
  5. On failure, silently ignore (not critical)

**B. Session screen (`app/session/[id].tsx`)**
- After `sendMessage` resolves, if the session has no title, call `autoNameSession`
- Only auto-name on the **first** user message (track with a ref or store flag)
- Use `useRef` to gate: `const hasAutoNamed = useRef(false)`

**C. SDK (`src/lib/sdk.ts`)**
- `session.update` already exists — no changes needed

### Edge cases
- Title already set by user or server: don't overwrite
- Multiple rapid sends: `hasAutoNamed` ref prevents duplicate calls
- Server returns 404 on update (older servers): silently ignore

## 3. Session Tags / Labels

**Design**: Free-form tags stored per-session. Tags appear as chips in the session list. Stored in SecureStore, not synced to server.

### Changes

**A. Types**
- Add `tags: string[]` to `ServerConnection`? No — tags are per-session, not per-connection.
- Add `tags` field to `Session` interface in `src/lib/sdk.ts`? No — server doesn't support it yet.
- Store tags in `src/stores/sessions.ts` as a separate `Record<string, string[]>` map (sessionID → tags), persisted to SecureStore.

**B. Store (`src/stores/sessions.ts`)**
- Add state: `sessionTags: Record<string, string[]>`
- Add actions:
  - `setSessionTags(sessionID: string, tags: string[])`
  - `addSessionTag(sessionID: string, tag: string)`
  - `removeSessionTag(sessionID: string, tag: string)`
- Persist to SecureStore key `opencode_session_tags_v1`
- Load on module init

**C. Session list UI (`app/(tabs)/index.tsx`)**
- In `SessionItem`, render tags as small chips below the title
- Chips styled with accent color border/bg, small font
- On tap of a tag chip: filter session list to that tag
- Add a "Add tag" option in the session long-press menu
- Tag input: simple `TextInput` in an `Alert.prompt` or bottom sheet

**D. Session detail UI (`app/session/[id].tsx`)**
- Show current tags in SessionInfo panel
- Allow adding/removing tags from the session info screen

**E. Filtering**
- Add tag filter bar at top of session list (only visible when a tag filter is active)
- Clear filter button

### Edge cases
- Tag with spaces: normalize to lowercase, trim
- Duplicate tags: deduplicate on add
- Empty tag: ignore
- Server session list refresh: preserve local tags (they're stored by sessionID, not by index)

## Validation

1. **Reply/thread**: Long-press any message → "Reply" appears in action sheet → tapping it sets quoted preview in composer → sending prepends quoted text → assistant receives it in context
2. **Auto-naming**: Create new session → send "Fix the auth bug in login.ts" → session title auto-updates to "Fix the auth bug in login.ts" (or truncated variant)
3. **Tags**: Long-press session → "Add tag" → enter "project-foo" → chip appears in session list → tap chip → list filters to tagged sessions

---

## Out of Scope

- Visual thread nesting (deferred to future pass)
- LLM-based session summarization for titles (simple truncation only)
- Server-side tag sync (tags are local-only)
- Tag autocomplete/suggestions
